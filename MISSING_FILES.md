# Missing / newly created files and gaps

Generated after bringing the project up on this machine and running the full
evaluation study end to end. Everything listed here is either a file that did not
exist and now does, or a gap that is still open. Nothing on this page is a
speculation: each item was found by running the code.

### Rewritten rather than created

`experiments/datasets/evaluation.csv` now contains **12 queries with real ground
truth** for the video that is actually indexed. Each row's `notes` column states
which keyframes were inspected and, importantly, which nearby keyframes were
**deliberately excluded** and why. Annotation was done by reading full-resolution
frames extracted from the source video, not by accepting the retriever's own
top-ranked suggestions - taking rank 1 as ground truth would grade the system on
its own output and make the metrics meaningless.

## 2. Defects found and fixed

These are the reason the project could not run. Each one is a real bug, not a
configuration problem.

| # | File | Defect | Effect | Fix |
|---|---|---|---|---|
| 1 | `backend/app/services/model_service.py` | `get_text_features()` / `get_image_features()` are called as if they return a tensor. In `transformers` 5.x they return `BaseModelOutputWithPooling`. | **Every** image and text embedding raised `AttributeError: 'BaseModelOutputWithPooling' object has no attribute 'norm'`. Nothing could be indexed or searched. `requirements.txt` pins `transformers>=4.45.0` with no upper bound, so both shapes are reachable. | Added `_as_embedding_tensor()`, which accepts a tensor or unwraps `.pooler_output`, and raises on anything else instead of silently coercing. |
| 2 | `backend/app/services/search_service.py` **and** `graph_search_service.py` | SQL used `f.embedding <=> :emb::vector`. SQLAlchemy's bind-parameter regex is `(?<![:\w$]):(\w+)(?!:)`; the `(?!:)` lookahead exists so PostgreSQL's `::` cast is not read as a bind parameter. `:emb` is followed by `:` so it never bound. | Both search routes returned **HTTP 500** (`syntax error at or near ":"`) against a live database. The frozen baseline was broken too, not just the new graph path. | Replaced with `CAST(:emb AS vector)` - identical SQL, binds correctly. |
| 3 | `backend/app/services/search_service.py` and `graph_search_service.py` | Thumbnail URL built with `thumb.split('/')[-1]`, but `thumbnail_path` is written by `os.path.join` and therefore contains **backslashes on Windows**. | URLs came out as `/media/frames/<id>/data\frames\<id>\00002151.jpg`. Every thumbnail 404'd in the UI. | Added `_thumbnail_basename()` in both services, which normalises `\` to `/` before taking the basename, so Windows and Linux rows agree. |
| 4 | `backend/tests/conftest.py` | Only `backend/` was added to `sys.path`. `tests/test_metrics.py` and `tests/test_reporting_and_plots.py` import `experiments.*`, which lives in the repo root. | Those two modules failed at collection with `ModuleNotFoundError: No module named 'experiments'`, so **the metrics and figure tests never ran**. The documented "178 tests pass" was not achievable. | Also insert the repo root, which is what the module's own docstring already promised ("runs identically from the repo root and from `backend/`"). |
| 5 | `experiments/evaluation/evaluate_retrieval.py` | `_live_condition()` read a condition's `RankingConfig` and then never passed it to `graph_search()`. | All four ablation conditions ran with the **production** weights while the results table printed the per-condition weights. The ablation table did not describe the code that produced it. | `_live_condition()` takes `config=` and forwards it; each condition and each depth-sweep point now runs with the weights it is labelled with. |
| 6 | `backend/test_gpu.py` | An exploratory SigLIP-2 smoke script named `test_*.py`, so pytest collected it and executed it at **collection** time. | `pytest backend` from the repo root aborted with `FileNotFoundError: test.jpg` (the script opens that file by relative path), and `cd backend && pytest` wasted ~2 min loading the 1.5 GB checkpoint to then report "no tests ran". | Added `backend/conftest.py` with `collect_ignore = ["test_gpu.py"]`. The script is untouched and still runnable via `cd backend && python test_gpu.py`. |

Defects 4 and 6 together mean the documented "178 tests pass" was not reliably
achievable from the repo root — the suite aborted during collection before a
single test ran.

Defect 5 was only visible *after* defects 1-3 were fixed. Before them the run
crashed, so the inconsistency had never been exercised.

## 3. Gaps that are still open

These are **not** fixed. They are honest limitations of what was measured.

### 3.1 Environment: pgvector was unavailable and is now provided differently

`scripts/README.md` records pgvector as a hard blocker on this machine: no C
compiler, no Docker, and `C:\Program Files\PostgreSQL\18\share\extension` is not
writable without administrator rights. That is now resolved, but **not** the way
the project documents.

PostgreSQL + pgvector 0.6.0 now runs **inside WSL2** (Ubuntu 24.04, PostgreSQL
16) on port **5433**, with `pg_hba.conf` opened to the WSL subnet. `.env` points
at it. Consequences:

* The Windows-side PostgreSQL 18 on 5432 is still there and still has no pgvector.
* **WSL2 assigns a new IP on every boot.** After a reboot, re-check it with
  `wsl -u root -- hostname -I` and update `DATABASE_URL` in `.env`.
* WSL2 suspends when idle and Windows then loses the route to the database. A
  keepalive is needed; a `sleep`-based loop inside WSL is enough.
* This is a workstation workaround. **On a normal deployment the documented
  Docker path (`docker compose up --build`, `pgvector/pgvector:pg16`) remains the
  supported route**, and nothing in the code was changed to accommodate WSL.

### 3.2 The concept layer is still empty

No detector, OCR engine, ASR model or captioner exists, so `DEPICTS` edges are
never written and `CONCEPT`/`OBJECT`/`TEXT` nodes stay empty. Confirmed by
inspection, not assumed: all 40 graph nodes are `VIDEO`/`SCENE`/`FRAME`, and all
node confidences are exactly `1.0`. `ConfidenceScore` is therefore a constant and
cannot influence ranking. The ablation correctly sets its weight to `0`.

### 3.3 Graph re-ranking did not change the ordering - measured, not assumed

This is the most important negative result, so it is stated plainly:

> On this corpus, **all four ablation conditions produce the same Recall@10
> (0.1042), Precision@10 (0.0917) and NDCG@10, and all four graph depths
> (0, 1, 2, 3) return byte-identical orderings.**

It was verified by instrumenting the pipeline, not inferred from the tables. The
cause is visible in the per-candidate scores for a single query:

```
#1 t=74.7 final=0.2499 vec=0.0171 graph=0.7438 temp=0.4 conf=1.0
#2 t=71.7 final=0.2497 vec=0.0169 graph=0.7438 temp=0.4 conf=1.0
#3 t=65.7 final=0.2497 vec=0.0168 graph=0.7438 temp=0.4 conf=1.0
```

`graph_score` is **identical to four decimal places for every candidate**, and
`temporal_score` is identical too, so both terms are constants. A constant cannot
change a ranking. Two independent reasons:

1. **One SCENE node for the whole video.** Scene clustering uses a 3.0 s window
   and retained keyframes are ~3.0 s apart, so every frame chains into a single
   scene. `SceneOverlap` is then 1.0 for everyone.
2. **Frames are near-duplicates.** Every frame is a screenshot of the same dark
   application, so measured cosines cluster tightly (the top candidates sit
   within 0.0161-0.0171). The graph faithfully records that they *are* similar;
   similarity carries no ranking signal when it is true of everything.

This is a property of **this corpus**, not proof that graph re-ranking is
useless. A corpus with genuinely distinct shots would separate the conditions.
It does mean **no claim of retrieval improvement is supported by the present
data**, and none is made.

### 3.4 `Makefile` targets do not work on Windows

`make eval`, `make plots`, `make backend`, `make test` and `make clean` all use
POSIX shell syntax (`mkdir -p`, `. .venv/bin/activate`, `rm -rf`, a `for` loop
with `plot_$$s`). None of it runs in PowerShell, and `make` is not installed on
this machine either. `RUN.ps1` provides the equivalent workflow natively. The
`Makefile` is left untouched because it is presumably correct for the Linux/Docker
path, which remains the documented deployment route.

### 3.5 Absolute retrieval quality is low, and the reason is the corpus

Recall@10 is `0.104` and MRR `0.100`. For scale, a random ranker over 38
keyframes returning 10 would score about `0.26` Recall@10, so the system is
**below** the random baseline on this video. That is a real, unflattering
measurement and it is reported rather than hidden.

Two contributing causes, both properties of a single screen-recording clip:

* Keyframes are thumbnails of a **dark-themed UI**. The distinguishing evidence
  ("Generating script using AI...", "MOX LOG", a single dropdown) is a handful
  of pixels tall at 320x180, so the image tower cannot see it.
* SigLIP-2 text-image cosine scores here are `0.006-0.017`, a very narrow band,
  which is the signature of a weak signal.

### 3.6 Latency is dominated by a one-off model load

Condition A shows `avg 7633 ms` and `P95 ~26000 ms` against `B/C/D` at
`79-234 ms`. The first query loads the ~1.5 GB checkpoint into GPU memory
(~25 s); every later query runs at ~130-160 ms. The A/C/D columns are *not*
comparable as written because A happened to execute first and absorbed the load.
A fairer comparison would warm the model before the first measured query - the
warm-up call in `main.py` is still commented out, as the README notes. Reported
here rather than silently corrected, because changing the harness's timing
semantics is a decision for the project, not a bug fix.

### 3.7 Storage metrics are partial

`frame_reduction_percent` and graph sizes are real (`3108 -> 38` frames,
`98.78%` reduction, 40 nodes, 270 edges). But `raw_video_bytes` and
`storage_overhead_ratio` are `N/A` because `collect_indexing_metrics()` calls
`os.path.getsize(video.path)` and the stored path is relative to the backend CWD
(`data/media/<uuid>.mp4`). The process was started from `backend/`, so the path
*is* resolvable in principle, but the report still emitted `N/A`; the exact cause
was not isolated. `derived_bytes` (`175104`) is real.

### 3.8 `db_session` fixture is defined but never used

`backend/tests/conftest.py` defines a `db_session` fixture gated behind
`VIDEOCTRLF_RUN_DB_TESTS=1`. **No test in the suite requests it.** Running the
suite with that variable set yields the same 178 passing tests. So the
"database-backed tests (opt-in)" documented in `AGENT.md`, `Readme.md` and
`NATIVE_SETUP.md` **do not exist**. This is why defect 2 - a 500 error on every
live search - survived a suite of 178 green tests.

Worth fixing by adding a real integration test that asserts
`POST /api/v1/search` returns 200 against a live database. It would have caught
two of the five defects above immediately.

### 3.9 SigLIP vs SigLIP-2 comparison is still `N/A`

Only one checkpoint has been indexed. Populating it means re-embedding the same
keyframes with `google/siglip-so400m-patch14-384` and scoring both on identical
queries; the harness reports `N/A` with that reason rather than inventing a row.
Not attempted here.

### 3.10 Twelve queries is a demonstration, not a benchmark

The honest caveat already in `Readme.md` applies with full force. The numbers
above are single observations on one video. No confidence interval is computable
from `n=12`, and none is quoted.

### 3.11 No authentication, rate limiting, TLS or backup

Unchanged from the documented production checklist. The API is fully open and
anyone who can reach the port can upload and search.

## 4. Minor observations

* `experiments/results/graph_results.csv` carries a leading row for depth `2`
  with every metric `N/A`, ahead of the real depth-2 row. It comes from the
  `--graph` block writing an aggregate row that is then also written by
  `--depth-sweep`. Cosmetic - the values are consistent - but the first data row
  of a CSV should not be an all-`N/A` duplicate.
* `README.md` and `Readme.md` both exist as tracked files. On a
  case-insensitive filesystem these are the same path; on Linux they are two
  files with near-duplicate content, which is a trap for anyone cloning the repo.
* `thumbnail_path` is stored **relative** to the backend CWD. That is
  Docker-friendly but means the stored rows are only meaningful relative to the
  directory the process was launched from.
